Service Level Agreement (SLA) ini menjelaskan komitmen ketersediaan dan respons CipherVault. Dokumen ini berlaku untuk versi layanan saat ini dan dapat disesuaikan seiring pertumbuhan infrastruktur.

1. Definisi Layanan

Layanan mencakup komponen berikut yang dipantau ketersediaannya:

  • API aplikasi (upload, download, share, manajemen file).
  • Dashboard frontend.
  • Autentikasi (login, register, API Key).
  • Database penyimpanan metadata dan kunci terbungkus.
  • Storage file terenkripsi (ciphertext).

Indikator kesehatan tersedia di endpoint publik: /health/live dan /health/ready.

2. Target Uptime

TingkatUptimeDowntime/bulan
Target99,5%≈ 3,6 jam
Aspirasi99,9%≈ 43 menit

Uptime diukur selama periode kalender bulanan, mengecualikan maintenance terjadwal (lihat bagian 4).

3. Kategori Downtime

  • Planned Maintenance: downtime terjadwal yang diumumkan sebelumnya. Tidak dihitung dalam perhitungan uptime.
  • Unplanned Incident: gangguan tak terduga (mis. crash, kegagalan database). Dihitung penuh dalam uptime.
  • Partial Degradation: sebagian fitur bermasalah namun inti layanan tetap berjalan.

4. Maintenance Window & Notifikasi

  • Jadwal: maintenance rutin dilakukan pada jam sepi (mis. 02:00–05:00 WIB) bila memungkinkan.
  • Notifikasi: minimal 48 jam sebelumnya untuk maintenance terjadwal melalui email terdaftar dan/atau banner aplikasi.
  • Darurat: pemeliharaan kritis (mis. tambal kerentanan) dapat dilakukan dengan notifikasi sesingkat mungkin.

5. Response Time untuk Laporan Insiden

TingkatContohRespons
P1Layanan tidak bisa diakses total≤ 1 jam (konfirmasi)
P2Fitur utama bermasalah≤ 4 jam
P3Gangguan minor / pertanyaan≤ 24 jam

6. Yang Tidak Dicakup SLA (Eksklusi)

  • Force majeure: bencana alam, gangguan infrastruktur internet, atau peristiwa di luar kendali wajar.
  • Misconfiguration pengguna: kesalahan konfigurasi, kredensial hilang, atau penyalahgunaan API.
  • Outage pihak ketiga: gangguan penyedia DNS, certificate authority, atau layanan upstream.
  • Insiden keamanan aktif: saat sedang dalam respons insiden (lihat Prosedur Data Breach), stabilitas dapat sementara dikorbankan demi kontainment.

7. Metrik Pengukuran

  • Uptime: dihitung dari probing endpoint /health/ready secara berkala.
  • Latency: waktu respons rata-rata API (best-effort dipantau, tidak menjadi jaminan eksplisit pada versi ini).
  • Error rate: rasio request gagal (5xx) terhadap total request.

8. Komunikasi Status

  • Status page: halaman status akan disediakan untuk transparansi uptime historis.
  • Notifikasi insiden: email kepada pengguna terdampak saat insiden P1/P2.
  • Post-mortem: ringkasan insiden signifikan dipublikasikan setelah selesai.

This Service Level Agreement (SLA) describes CipherVault's availability and response commitments. This document applies to the current version of the service and may be adjusted as infrastructure grows.

1. Service Definition

The service includes the following monitored components:

  • Application API (upload, download, share, file management).
  • Frontend dashboard.
  • Authentication (login, register, API Key).
  • Database for metadata and wrapped key storage.
  • Encrypted file storage (ciphertext).

Health indicators are available at public endpoints: /health/live and /health/ready.

2. Uptime Target

TierUptimeDowntime/month
Target99.5%≈ 3.6 hours
Aspirational99.9%≈ 43 minutes

Uptime is measured over calendar monthly periods, excluding scheduled maintenance (see section 4).

3. Downtime Categories

  • Planned Maintenance: scheduled downtime announced in advance. Not counted toward uptime calculations.
  • Unplanned Incident: unexpected disruptions (e.g., crashes, database failures). Fully counted toward uptime.
  • Partial Degradation: some features malfunctioning while core service remains operational.

4. Maintenance Window & Notifications

  • Schedule: routine maintenance is performed during off-peak hours (e.g., 02:00–05:00 WIB) when possible.
  • Notification: at least 48 hours in advance for scheduled maintenance via registered email and/or in-app banner.
  • Emergency: critical maintenance (e.g., vulnerability patches) may be performed with as little notice as possible.

5. Incident Report Response Time

TierExampleResponse
P1Service completely inaccessible≤ 1 hour (acknowledgment)
P2Major feature impairment≤ 4 hours
P3Minor disruption / inquiry≤ 24 hours

6. SLA Exclusions

  • Force majeure: natural disasters, internet infrastructure disruptions, or events beyond reasonable control.
  • User misconfiguration: configuration errors, lost credentials, or API misuse.
  • Third-party outages: disruptions from DNS providers, certificate authorities, or upstream services.
  • Active security incidents: during incident response (see Data Breach Procedure), stability may be temporarily sacrificed for containment.

7. Measurement Metrics

  • Uptime: calculated from periodic probing of the /health/ready endpoint.
  • Latency: average API response time (best-effort monitored, not an explicit guarantee in this version).
  • Error rate: ratio of failed requests (5xx) to total requests.

8. Status Communication

  • Status page: a status page will be provided for historical uptime transparency.
  • Incident notifications: email to affected users during P1/P2 incidents.
  • Post-mortem: summary of significant incidents published after resolution.
