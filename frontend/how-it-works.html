Encryption Works

Arsitektur hibrida UHC + AES + RSA Hybrid architecture UHC + AES + RSA

CipherVault menggunakan arsitektur enkripsi hibrida tiga lapis yang dirancang untuk zero-knowledge storage. Setiap file melalui pipeline tetap: AI Selector → UHC → AES-256-CBC → RSA Key Wrapping. Urutan ini selalu sama — tidak ada algoritma yang dipilih atau diganti secara dinamis.

E Alur Enkripsi (Upload)

1

AI Selector

AI Selector bukan pemilih algoritma. Ia hanya menganalisis file untuk menentukan parameter UHC yang optimal.

extract_features() — Membaca ukuran, entropy, dan tipe file

adaptive_matrix() — Menentukan ukuran matriks UHC (M)

select_r() — Menentukan parameter r untuk Logistic Map

2

Generate Session Key

Membangkitkan kunci acak 32 byte yang unik untuk setiap file. Kunci ini digunakan sebagai seed untuk UHC dan key untuk AES.

3

Lapisan 1: UHC (Inner Layer)

Unimodular Hill Cipher bekerja di modulus 257 — byte 0–255 dinaikkan menjadi 1–256 agar matriks kunci selalu bisa di-invert saat dekripsi.

Logistic Map PRNG dengan seed = Session Key, parameter = r

Membangun matriks unimodular berukuran M × M

Mengenkripsi plaintext → menghasilkan intermediate ciphertext

4

Lapisan 2: AES-256-CBC (Outer Layer)

Mengenkripsi intermediate ciphertext dari UHC menggunakan Session Key. Menghasilkan final ciphertext yang disimpan ke disk.

5

Key Wrapping

Session Key tidak pernah disimpan dalam keadaan plain. Dibungkus tergantung siapa yang akan mengakses:

Owner

AES-ECB(PBKDF2(password))

Session Key dibungkus dengan key derivasi dari password user

Sharing

RSA-OAEP 2048-bit

Session Key dibungkus dengan public key penerima

6

Simpan

Ciphertext disimpan ke disk. Wrapped key, metadata (M, r, IVs, SHA-256 hash), dan info file disimpan ke database. Plaintext tidak pernah disimpan.

D Alur Dekripsi (Download)

1

Key Unwrapping

Membuka bungkus Session Key berdasarkan peran pengguna:

Owner

AES-ECB_Decrypt(PBKDF2(password))

Recipient

RSA-OAEP_Decrypt(private key)

2

Baca Metadata

Mengambil nilai M (ukuran matriks), r (parameter logistic), dan IVs dari database untuk merekonstruksi kunci UHC.

3

Balikkan Lapisan 2: AES-256-CBC

Mendekripsi ciphertext menggunakan Session Key → menghasilkan intermediate ciphertext.

4

Balikkan Lapisan 1: UHC

Merekonstruksi matriks unimodular dari Session Key, r, dan M. Melakukan UHC decrypt → menghasilkan plaintext.

5

Verifikasi Integritas

Menghitung ulang SHA-256 dari plaintext hasil dekripsi dan membandingkannya dengan hash yang tersimpan. Jika tidak cocok → file ditolak.

Konsep Kunci

Mod 257

UHC menggunakan modulus 257 (prima) bukan 256. Byte 0–255 dinaikkan menjadi 1–256 sebelum operasi matriks, menjamin setiap matriks kunci memiliki inverse — syarat mutlak agar dekripsi selalu berhasil.

Logistic Map

PRNG chaos-based yang menghasilkan deret pseudo-acak dari seed (Session Key) dan parameter r. Digunakan untuk membangun matriks UHC yang unik per file.

Zero-Knowledge

Server tidak pernah melihat plaintext, password, atau session key dalam keadaan plain. Semua kunci dibungkus (wrapped) sebelum disimpan ke database.

Double Key Wrapping

Session Key dibungkus dua cara: owner menggunakan password-derived key (PBKDF2), penerima sharing menggunakan RSA public key. Memungkinkan sharing tanpa mengungkap password.

CipherVault uses a three-layer hybrid encryption architecture designed for zero-knowledge storage. Every file follows a fixed pipeline: AI Selector → UHC → AES-256-CBC → RSA Key Wrapping. This order is always the same — no algorithm is selected or swapped dynamically.

E Encryption Flow (Upload)

1

AI Selector

The AI Selector does not choose algorithms. It only analyzes the file to determine optimal UHC parameters.

extract_features() — Reads file size, entropy, and type

adaptive_matrix() — Determines UHC matrix size (M)

select_r() — Determines parameter r for Logistic Map

2

Generate Session Key

Generates a unique random 32-byte key for each file. This key serves as the seed for UHC and the key for AES.

3

Layer 1: UHC (Inner Layer)

Unimodular Hill Cipher operates in modulus 257 — bytes 0–255 are elevated to 1–256 so the key matrix can always be inverted during decryption.

Logistic Map PRNG with seed = Session Key, parameter = r

Builds a unimodular matrix of size M × M

Encrypts plaintext → produces intermediate ciphertext

4

Layer 2: AES-256-CBC (Outer Layer)

Encrypts the intermediate ciphertext from UHC using the Session Key. Produces the final ciphertext stored to disk.

5

Key Wrapping

The Session Key is never stored in plaintext. It is wrapped depending on who will access it:

Owner

AES-ECB(PBKDF2(password))

Session Key wrapped with password-derived key

Sharing

RSA-OAEP 2048-bit

Session Key wrapped with recipient's public key

6

Save

Ciphertext is saved to disk. Wrapped key, metadata (M, r, IVs, SHA-256 hash), and file info are saved to the database. Plaintext is never stored.

D Decryption Flow (Download)

1

Key Unwrapping

Unwraps the Session Key based on the user's role:

Owner

AES-ECB_Decrypt(PBKDF2(password))

Recipient

RSA-OAEP_Decrypt(private key)

2

Read Metadata

Retrieves M (matrix size), r (logistic parameter), and IVs from the database to reconstruct the UHC key.

3

Reverse Layer 2: AES-256-CBC

Decrypts ciphertext using the Session Key → produces intermediate ciphertext.

4

Reverse Layer 1: UHC

Reconstructs the unimodular matrix from Session Key, r, and M. Performs UHC decrypt → produces plaintext.

5

Verify Integrity

Recalculates SHA-256 from the decrypted plaintext and compares it with the stored hash. If it doesn't match → the file is rejected.

Key Concepts

Mod 257

UHC uses modulus 257 (prime) instead of 256. Bytes 0–255 are elevated to 1–256 before matrix operations, guaranteeing every key matrix has an inverse — an absolute requirement for decryption to always succeed.

Logistic Map

A chaos-based PRNG that generates a pseudo-random sequence from a seed (Session Key) and parameter r. Used to build a unique UHC matrix per file.

Zero-Knowledge

The server never sees plaintext, passwords, or session keys in plain form. All keys are wrapped before being stored in the database.

Double Key Wrapping

The Session Key is wrapped two ways: the owner uses a password-derived key (PBKDF2), while sharing recipients use an RSA public key. This enables sharing without exposing passwords.
